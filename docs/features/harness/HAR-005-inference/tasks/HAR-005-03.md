# Task: HAR-005-03 — Persistent Hosting Topology & Graceful Shutdown

### Task ID
`HAR-005-03`

### Parent feature
`HAR-005` — [SPEC.md](../SPEC.md)

### Objective
Implement independent hosting lifecycle management and graceful shutdown handling for the Harness runner host, ensuring that active writer claims and in-flight operations are cleaned up cleanly on SIGINT/SIGTERM without leaving corrupted checkpoints.

### Current implementation
- `HarnessService` currently runs in-process inside the Gateway Next.js server instance.
- In `src/lib/harness/service.ts`, `shutdown()` is a no-op placeholder relying on the Gateway run service to abort active signals.
- In `src/lib/harness/journal.ts`, claims use generation fencing with `expiresAt`. If a process dies abruptly, the claim remains locked until the lease expires (15s fixture default).

### Dependencies
- Prior task IDs: `HAR-005-02` (`DONE`).
- Required contracts: `HarnessClaim`, `IHarnessJournal` in `src/lib/harness/contracts.ts`.

### Files to inspect
- `src/lib/harness/service.ts` — Harness service lifecycle and runner invocation.
- `src/lib/harness/journal.ts` — Claim and reclaim mechanisms.
- `src/lib/gateway/server/lifecycle.ts` — Gateway server shutdown hooks.

### Expected files to change
- `src/lib/harness/service.ts` — Implement active runner tracking and graceful drain on shutdown.
- `src/lib/harness/runner.ts` — Support graceful drain and checkpoint flush when cancellation signal aborts.
- `scripts/test-harness-lifecycle.mjs` — New test verifying shutdown and lease release.

### Implementation scope
1. Track active in-flight runner executions inside `HarnessService`.
2. On `shutdown()`:
   - Signal all active `AbortController` instances.
   - Wait up to a configurable timeout (e.g., 5 seconds) for runners to finalize their current step and flush checkpoints to disk.
   - For cleanly stopped runs, release writer claims immediately so subsequent processes do not wait out lease timeouts.
3. Test delayed redelivery: submit a run, trigger graceful shutdown mid-run, start a new service instance, call `recoverOpen()`, and assert that the run resumes from its last checkpoint.

### Out of scope
- Multi-node distributed worker clustering (Release 2 Orchestrator).
- Docker container orchestration or Kubernetes deployment manifests (owned by `INF-004`).

### Invariants
- A shutting-down worker must never overwrite a newer generation claim.
- Final checkpoint must accurately reflect whether execution was interrupted or completed.

### Acceptance criteria
- [ ] 1. Calling `HarnessService.shutdown()` aborts in-flight inference and waits for runners to yield.
- [ ] 2. Checkpoints are flushed to storage with status `interrupted` or `cancelled`.
- [ ] 3. Claims are released or marked reclaimable immediately upon clean shutdown.
- [ ] 4. A new service instance successfully resumes open runs via `recoverOpen()` without waiting for lease expiration.
